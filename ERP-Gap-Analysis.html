The headline

I expected this analysis to conclude “add MRP, add batch tracking, add quality inspection” — the things ERPNext and Odoo ship that you don't. Those gaps are real and they're in Tier 4 below. But the audit surfaced three findings that outranked every feature request:

  • RBAC was fully written and never called. permissions.py defined 18 modules and 9 roles. deps.py defined require_module(). That function was referenced exactly once in the entire backend — at its own definition. All 107 protected endpoints used Depends(get_current_user) only. Fixed — 103 routes now enforce a module.
  • Two code paths actively corrupted data every time they ran, and one of them silently doubled finished-goods stock. Both fixed, with the backfill verified against live data first.
  • Your GST output is structurally wrong. One flat percentage, no CGST/SGST/IGST split, and the PDF hardcodes the label “IGST” regardless of place of supply. Still open — Tier 2.

The market comparison is genuinely useful — but it mostly tells you that commercial ERPs solved these particular problems two decades ago, and that the distance between you and them is smaller than it looks once these are closed. Read Tier 0 as bugs, not roadmap.

One pattern worth carrying forward from fixing them: in all three cases the data changed the plan. The role audit was safe to land only because all five real users already resolved through their database role, so removing the e-mail matching changed nothing. The status backfill only became defensible after a query revealed that 713 of 838 orders held a legacy code with no payment meaning. Neither fact was visible in the code.

Added

Login brute-force throttle

done · be2e6eb

Not in the original audit, but /auth/login is now one of only two endpoints reachable without a token, which makes it the brute-force target. Added a sliding window of 8 failures per 15 minutes, keyed on both client IP and username so rotating source IPs against one account still trips it.

Caveat, documented in the code: state is per-process, so behind multiple workers the effective limit multiplies by worker count. It raises brute-force cost substantially but is not a distributed limiter — move to Redis if the API is scaled out horizontally.

Fixed

Payment status and dispatch status share one column

done · 1297173
app/routers/sales_orders.py:380 vs :498-505 · migration 008

PATCH /payment wrote payment state (1–3) into sales_orders.status. POST /dispatch wrote dispatch state (3–4) into the same column. Analytics read it as payment status only. Recording a dispatch destroyed the payment state, and recording a payment destroyed the dispatch state.

This was live, not theoretical. Querying the data first showed 41 orders fully dispatched and 23 of those also payment-received — two facts sharing one integer. Dispatching any of them would have wiped the payment state.

The query also changed the backfill plan. 713 of 838 orders carry status = 6 — a value no code path writes, from a legacy bulk import. It holds no payment meaning, so those rows were left NULL rather than asserting "not received" about 713 real orders. dispatch_status was derived from sales_order_items.dispatched_qty, the actual record of what shipped, rather than from the conflated column.

Fixed in 1297173: split into payment_status and dispatch_status with CHECK constraints on both, so neither can accumulate an out-of-range code the way status accumulated a 6. status is kept and still mirrored from payment_status so unmigrated readers keep working — and since only the payment endpoint writes it now, the collision cannot recur. Two things fell out: payment_received had existed since the initial schema but no endpoint ever wrote it (FALSE on all 838 rows) and is now derived; and analytics was bucketing on status IN (1,2,3), so 85% of orders were missing from the payment breakdown entirely — they are now reported explicitly.

Fixed

Issue-then-complete a work order and stock doubles

done · 1297173
app/routers/work_orders.py:318-408 · /issue-products

POST /issue-products inserts finished-goods rows and deducts no materials. Marking the same work order complete inserted finished-goods rows again for the full ordered quantity and deducted materials once. A fully-issued work order that was then completed produced its output twice while consuming input once.

Fixed in 1297173: completion now produces only the outstanding quantity — remaining_qty, which _load_wo already computed — so issued + produced always equals ordered.
Material consumption was corrected at the same time: requirements are now aggregated per material across all products before validating, because one material appearing in two products' BOQs previously passed two per-line checks and still drove the total negative. Insufficient stock rejects with the per-material shortfall instead of going negative; a BOQ material missing from inventory rejects instead of continue (which silently under-consumed and hid a broken BOQ→material name link); and rows are locked FOR UPDATE before deducting.
Reopening a completed order is now refused rather than left inconsistent — completion has no reversal and the goods may already be sold. Safe to refuse because the UI only ever sends "completed".

~15 minutes

Tier 1

The foundations every market ERP has

Next 4–6 weeks

These are what separate “a set of CRUD screens over a database” from “an ERP.” The stock ledger is the highest-leverage single change in this entire document — it unlocks valuation, reconciliation, traceability, and batch tracking, all of which are otherwise impossible to add later.

Foundation

An immutable stock movement ledger

~2 weeks

Today stock is a single mutable balance — materials.length_weight_nos and finished_goods.quantity_in_stock — incremented and decremented in place from nine call sites across five routers. There is no movement history, so a wrong number cannot be traced to a cause, and current stock cannot be reconciled against anything. ERPNext and Odoo both ship a full stock ledger with FIFO/LIFO/moving-average valuation and landed costs.

Fix: add stock_ledger_entries (item, qty delta, unit, source doc type + id, user, timestamp, resulting balance). Route all nine mutation sites through one function that writes a ledger row. Keep the balance column as a cached projection you can rebuild from the ledger.

Foundation

Audit trail — who changed what

~1 week

No table has created_by or updated_by. There is no audit or history table anywhere. When a price or a quantity is wrong, there is no way to establish who changed it or when. Audit readiness for SMEs fails on exactly this — not missing transactions, missing traceability.

Fix: add created_by/updated_by/updated_at to every business table, plus an append-only audit_log for status transitions and price changes. You have the user on every request already.

Foundation

Materials are joined to everything by name string

~1 week
products.py:309 · purchase_orders.py:367,442 · work_orders.py:355 · finished_goods.py:153

BOQ lines, PO lines, work-order consumption, and finished-goods returns all locate a material with LOWER(name) = LOWER(name). There is no foreign key. Renaming a material silently orphans its BOQ lines and its cost history — and BOQ explosion then skips it without error. Supplier auto-creation by name has the same flaw: a rename spawns a duplicate supplier.

Fix: add real material_id FKs, backfill by name once, keep name as display only. Also validate the three NOT VALID FKs already in the schema.

Foundation

Document numbering is client-side and racy

~3 days

Four of five document types need a manually typed number. Offer numbers are suggested from rows currently loaded in the browser (offers/page.tsx:327). Enquiry numbers use MAX(SPLIT_PART(...)) + 1 with no lock. Every uniqueness check is read-then-insert. Two users creating documents at once will collide.

Fix: one number_series table (prefix, fiscal year, counter) and a server-side allocator using a Postgres sequence or SELECT … FOR UPDATE. Never let the client propose a number.

Foundation

Schema lives in five places, one of which runs DDL per request

~3 days

backend/migrations/ does not contain your core schema — files 001–007 reference products, sales_orders, and the offer_status enum without ever creating them. The real schema is spread across supabase/migrations/, a 68 KB pg_dump, four ad-hoc Python scripts, and email_campaigns.py:55-57, which executes CREATE TABLE IF NOT EXISTS plus ALTER TABLE on every list call. You also have 61 indexes including exact duplicates like idx_offers_idx_offer_status and idx_offers_idx_offers_status.

Fix: adopt Alembic, baseline from the live dump, delete the runtime DDL, and drop the duplicate indexes.

Tier 2

Compliance — where the market is genuinely ahead

Next quarter

This is the tier where a gap stops being a productivity cost and becomes a legal one. It is also where every Indian ERP — including free ERPNext — beats you outright today.

Your invoices may not be valid tax documents.

You apply one flat gst_pct per document. There is no CGST/SGST/IGST split and no place-of-supply logic, yet pdf_service.py:725 prints the label “IGST (x%)” on every invoice. For an intra-Rajasthan sale that label is simply wrong. Separately, hsn_code exists only in the frontend — hardcoded to "70199000", composed into description text, never sent to the API, and with no column in any table. Your company GSTIN, address, phone, and email are hardcoded in pdf_service.py.

You have no challan concept at all.

Tier 3

Accounting — and what not to build

Ongoing

The audit found no chart of accounts, no journal entries, no double-entry, no trial balance, no P&L, no balance sheet, no AR/AP aging, no credit notes, no vendor payments, and no bank reconciliation. That sounds alarming until you ask whether you should build any of it.

Recommendation: do not build a general ledger.

Tally already does this, your CA already knows it, and it is a deep, boring, heavily regulated domain where you have no advantage. Build the operational finance features that touch your workflow, and push the accounting layer out via export or integration.

Build these

  • Payment history as rows, not a scalar. Today payment_amount is a single overwritable number — part-payment history is destroyed. A payments table with date, method, reference, and allocation is a few days' work and makes collections real.
  • Due dates and AR aging. There is no due_date column anywhere, so no ERP-standard 0-30-60-90 bucket is computable. This is your single most valuable finance report.
  • Credit limits and payment terms on companies, with a soft warning at offer or order time.
  • Inventory valuation. Right now per_unit_cost is overwritten by the latest PO receipt, which destroys historical cost — so your /products/costs rollup silently reprices old production. Once the Tier 1 stock ledger exists, moving-average becomes straightforward and COGS becomes possible.

Skip these — integrate instead

  • Chart of accounts, journals, trial balance, P&L, balance sheet, cash flow
  • Bank reconciliation, cash and petty-cash books
  • TDS/TCS computation, fiscal period close, year-end

A Tally or Zoho Books export of invoices, payments, and purchase bills gets you the statutory layer for a fraction of the effort — and none of those exports exist yet, which makes this a cheap, high-value first step.

Tier 4

Manufacturing depth

6–12 months

This is the tier I expected to lead with. It matters — but every item here is easier once Tier 1 exists, and several are outright impossible without the stock ledger.

Priority

Quality inspection & batch traceability

~6 weeks

For an EN-131 / ANSI A-14.5 certified product line this is your largest uncovered risk. You manufacture load-rated safety equipment with no inspection checkpoints, no batch numbers, no supplier lot capture, and no certificate storage. If a ladder fails in the field you cannot scope which units share its material lot. Market ERPs use batch genealogy precisely to bound recall scope and satisfy ISO 9001 audits.

Fix: batch numbers on material receipt and on finished goods, an inspection record against work-order completion, and a genealogy query from FG batch back to supplier lot. Depends on the Tier 1 stock ledger.

Priority

Reorder points & safety stock

~2 weeks

Your low-stock thresholds are hardcoded constants — and inconsistently: 10.0 for materials and 5.0 for finished goods in dashboard.py, < 10 again in materials.py, but 5 in the finished-goods screen and < 10 in the inventory screen. The market standard is per-item reorder_point = (avg daily usage × lead time) + safety stock.

Fix: per-material reorder level and safety stock columns, plus supplier lead time. Cheap, and it turns your dashboard alert from decorative into actionable.

Later

Multi-level BOM, MRP, and capacity

~3 months

Your BOQ is single-level with no revisions or effectivity dates, and Work Orders have no planning layer above them. ERPNext runs MRP off demand, stock, and lead times to auto-generate work orders and POs, with finite capacity scheduling, Gantt views, and bottleneck analysis. This is the biggest genuine feature gap — and the one where buying beats building most decisively.

Fix: BOM revisions and sub-assemblies first (incremental, useful alone). Defer real MRP until order volume actually makes manual planning hurt.

Later

Multi-warehouse & bin locations

~4 weeks

Single flat stock pool today. Only worth building when you genuinely hold stock in more than one place — but note it is much cheaper to add on top of a stock ledger than to retrofit onto balance columns, which is another argument for sequencing Tier 1 first.

Tier 5

Where you could get ahead

Opportunistic

Everything above is catching up. These are places where a small custom system can genuinely beat a big commercial one, because you can ship them narrow and fit them exactly to E-SAFE.

  • Shop-floor mobile capture. Work-order completion is currently a status flip in a desktop form, so system state and shop-floor reality drift. Offline-first barcode capture for material issue and FG receipt would fix your inventory accuracy at the source — and it is a small app, not an ERP module.
  • Quote intelligence. Your per-company price-history chips are already better than stock ERPNext. Extend to win/loss by price point, margin floors, and discount approval thresholds — this is real CPQ territory, and it's your differentiator.
  • Offer revision history. Market CPQ preserves every version so you can see what moved between revision 1, 2 and 3. You overwrite in place.
  • Document extraction. Supplier invoice → PO match is the highest-ROI AI use case in ERP and a natural fit given you already parse CSV/XLSX.
  • Customer portal. Order status, dispatch tracking, and invoice download. Small surface, high perceived value, and you already have per-company auth.
  • Tests and CI — started. The audit found one test file covering 25 lines of pure arithmetic against 108 endpoints, with two of its seven test classes asserting against mocks the test itself constructs, so they could never fail. Tier 0 added 62 tests across authorization, login throttling, and the status/stock logic — each one negative- controlled, meaning the fix was reverted to confirm the test actually breaks. That is the difference worth preserving. Still missing: any HTTP-level test (no httpx, so no TestClient), any frontend test, and CI to run any of it — no Dockerfile, no workflow, no linter config. Before Tier 1 refactors touch nine stock-mutation sites, wire the suite into CI so it runs without being asked.
Verdict

Build, buy, or both

The honest read: do not chase feature parity with ERPNext. They have hundreds of contributor-years in inventory and accounting, they are free, and a 50-user shop saves ₹14–21 lakh a year choosing them over Odoo Enterprise. You will not out-build that on generic modules.

But you shouldn't migrate either. Your enquiry → offer → BOQ → work-order spine is modelled on how E-SAFE actually sells and builds ladders — spec slots, tender variants, per-company price history, BOQ unit conversion. That is exactly the case where custom wins, and it is the part a migration would destroy.

The split I'd recommend:

  • Keep and invest: CRM, enquiries, offers/CPQ, products & BOQ, work orders, the analytics suite.
  • Build properly, once: stock ledger, audit trail, RBAC enforcement, tax structure, invoicing. These are foundations, not features — they don't get cheaper later.
  • Integrate, don't build: general ledger and statutory reporting (Tally/Zoho Books export), e-invoice IRN and e-way bill (IRP provider API).
  • Defer until it hurts: MRP, capacity scheduling, multi-warehouse.
